## 一、阻塞清单（发 v1.0.0 前必须完成，共 8 项）

### P0-1 certbot 续期后 nginx 永不 reload —— 90 天后线上 TLS 必过期
- 证据：`deploy/bootstrap.sh:367-368` 的 `certbot certonly` 无任何 `--deploy-hook`；全仓库无 renewal-hooks 安装动作；本项目用 `--webroot` 模式，发行版 certbot 包的续期定时器不会自带 nginx reload。**且服务器已走进"证书已存在→跳过签发"分支（deploy-log 实证），今后修改 certonly 参数对这台机器永远无效**——必须走 hook 文件落盘路线。
- 修法：bootstrap 第 9 步前无条件幂等安装 `/etc/letsencrypt/renewal-hooks/deploy/10-reload-nginx.sh`（内容 `nginx -t && systemctl reload nginx`，先 -t 防坏配置牵连主站）；certonly 同步补 `--deploy-hook`；README:209 验收动作改为 `certbot renew --dry-run` + `openssl s_client` 看实际证书日期。

### P0-2 链接 URL 可注入 `javascript:` —— 已 PoC 实证的存储型 XSS
- 证据：`sources/feeds.py:111` 对 `link` 零协议校验，canonicalize 原样保留 `javascript:`；简讯 URL 不经 `safe_get` 白名单；三个渲染点（home/article/email 模板的 `href="{{ … }}"`）autoescape 挡不住 href 语境。生产站目前仅靠 nginx CSP `default-src 'self'` 单层兜底；本地 preview 与 `var/mail/*.html`（file:// 打开）完全无防护。
- 修法：`parse_feed` 对 link 做 `{http,https}` 白名单、不合格丢弃条目；加 `safe_url` Jinja 过滤器在模板兜底；补 `tests/unit/test_render_safety.py`（javascript: URL、标题 `<script>`、恶意实体），弥补 PLAN:104 承诺过但从未存在的安全测试。

### P0-3 全权限 GitHub token 被推到生产服务器 —— 供应链回环
- 证据：`deploy/deploy-all.ps1:167` 用 `gh auth token`（scope 含 repo+workflow）登录 GHCR 并 base64 驻留 `/root/.docker/config.json`；与 README:129 和 bootstrap:221 自定的"只读 read:packages"红线直接冲突。服务器沦陷 → 改 workflow/推 tag → CI 出恶意镜像 → 服务器自动拉取，回环成立。
- 修法：脚本改用专用只读 PAT（`ND_GHCR_TOKEN` 或交互输入）；**运维动作（本项含在 P0-8）：服务器 `docker logout ghcr.io`，GitHub 侧吊销当前 token，用 read:packages PAT 重登**。镜像已在本地时日常 timer 不需要 registry 凭据。

### P0-4 deploy-all.ps1 整体覆写生产 .env —— 每次部署静默抹掉面板改动
- 证据：`deploy-all.ps1:149-158` 用本机 `.env.local` 从零构造 10 行文件 scp 覆盖 `config/.env`；而面板"启用档案"正是定点改写该文件（OPERATIONS:114 定义为生产换密钥正式姿势）。面板切完供应商 → 下次 deploy.bat → 密钥被开发机旧值覆盖回去，无警告无备份。同时破坏 server-push.ps1:6"密钥不经本脚本"的声明。
- 修法（三选一，推荐①）：① 改定点合并只更新列出的 key、保留其余行；② 覆盖前先服务器侧带时间戳备份 + 控制台醒目警告；③ 移除 [3/6] 步，回归"密钥只在服务器端注入"红线。

### P0-5 镜像 digest 纪律未实现 + DEPLOYED.log 从未被写入 —— 回滚链是空的
- 证据：bootstrap 渲染的是 tag（`:v0.6.0rc6`，deploy-log 实证线上即 tag）；运维手工固定 digest 会被下次部署静默覆盖回 tag；README:226 承诺的发布台账 `backups/DEPLOYED.log` 全仓库只有 2 处引用、0 处写入——回滚指引让人去查一个不存在的文件。PLAN:473/476 两条验收标准（digest 一致性、回滚演练）当前无法满足。
- 修法：新增 `ND_WORKER_DIGEST/ND_WEB_DIGEST` 渲染 `@sha256:`；bootstrap 检测到"现有 compose 是 digest 而本次是 tag"时 die（需 `ND_ALLOW_TAG_DOWNGRADE=1` 显式放行）；bootstrap 收尾把日期/tag/两条 digest 追加进 DEPLOYED.log（`docker image inspect` 可取）；可选：CI release-bundle 附 `digests.env` 供 install.sh 自动喂入。**本项是回滚演练（发版门槛）的前置。**

### P0-6 SMTP TLS 不校验证书 —— 凭据可被中间人截获
- 证据：`delivery/mailer.py:54,58` 的 `SMTP_SSL`/`starttls` 均不传 context，CPython 默认走 unverified context（加密但不认证），`login()` 的凭据可被路径中间人拿走。
- 修法：两行——模块级 `_TLS = ssl.create_default_context()`，两处传入。

### P0-7 发版机械项 —— 同一坑已踩两次，1.0.0 最可能在这里翻车
- 版本号散落 5 处（`__init__.py`、bootstrap.sh:15、install.sh、deploy-all.ps1、README:46）而 CI 只校验第 1 处 → 漏改即"CI 绿灯、服务器仍拉 rc6"。修法：deploy-all.ps1 从 `__init__.py` 读版本去掉硬编码；bootstrap 第 10 步比对运行镜像的 version label 与 $TAG。
- 标签推送无前置检查（rc3 残留、rc4 分叉两次事故均源于此）：deploy-all.ps1 推 tag 前须校验"远端不存在同名 tag + 本地 tag 指向 HEAD + tag == __version__"，不满足即 die。
- 发版流程欠账：merge phase/7-deploy→main（落后 22 提交）、推送本地未推提交、打 `phase-7-accepted`、清理 phase/4 分叉、摘除各工件"服务器实测前不视为最终版"声明。

### P0-8 凭据轮换四件 —— 全部未做（运维动作，非代码）
SSH 密钥口令（030428 曾进会话）、DirectMail SMTP 密码、SUB2API key（轮换后直接面板粘贴，一分钟闭环）、**新增：gh 全权限 token（配合 P0-3：吊销 + docker logout + 只读 PAT 重登）**。这些凭据都曾进入会话/日志，发正式版前应清零历史暴露。

### 既定流程门槛（非新增，修完上述后按计划走）

## 二、非阻塞改进清单（按域分组，建议随 1.0.x 消化）

**供应链**：release.yml 8 处 action 改 SHA 钉版 + dependabot（与其自身"每环节可复现"注释对齐）；install.sh 改 `mktemp -d` + Release 附 sha256 校验 + `tar --no-same-owner`；bootstrap 生成口令改 `openssl passwd -stdin`（argv 可被本机 /proc 读取）。

**部署可靠性**：systemd 加 `OnFailure=` 告警（当前任务失败全靠人翻 journalctl，站点悄悄停更可能几天无人知）；nginx reload 失败后重跑因 cmp 相同被跳过、新配置永不生效的幂等空洞；ND_* 值白名单校验（`&` 会被 sed 静默错渲染）+ OWNER 强制小写；migrate_cfg 挪到 nginx 配置就位之后（升级路径半途失败会留下引用不存在文件的配置，殃及全局 nginx -t）；preflight 读 ND_*、补 8619 检查、修 IPv4/IPv6 误报（PLAN 挂账多轮）；server-push.ps1 ssh 显式透传 ND_*（当前主用路径参数化实际失效）。

**面板加固**：/admin/ 单独限速 zone（如 10r/m——现共用站点 10r/s，对口令爆破无实质抑制，news.conf:75 的注释与事实不符）；两处 CSP 加 `frame-ancestors 'none'`；面板脚本改静态 /admin/app.js 以去掉 unsafe-inline；配置写入改原子 + threading.Lock（多轮挂账）。

**流水线质量**：图片 URL 按 registry 已有 allowed_domains + https 过滤（现任意 https 主机可拿读者 IP）；slug 截断冲突加 URL 哈希后缀（同题材长标题会互相覆盖页面）；发布时间加上界钳制（`pubDate 9999 年`可永久霸占头条，PoC 实证）；重抓时 `INSERT OR REPLACE` 会把旧文 date 漂移到今天（改 `ON CONFLICT DO UPDATE` 不动 date）；DB/翻译缓存/邮件归档无保留策略且 build 全量重渲历史（增长线性放大 5 倍）；`SMTP_USE_TLS=false` 时应拒绝明文 login；`textutil.py:11-14` 先 clean 后 unescape 顺序反了（会把实体还原成裸标签存库，现靠 autoescape 单层兜底，属潜伏雷）；import-edition 对 date/slug 加校验（`../` 可写出目标目录，需操作者自导恶意 JSON 故不阻塞）+ 坏 JSON 干净报错；时区配置错误应在抓取前快速失败。

**文档批处理**：README 两处 06:30→08:00（同文件自相矛盾）；README:206 残留 Basic Auth `-u` 参数；OPERATIONS 命令表补 `import-edition`/`admin`/`--smoke`（9 个子命令只文档化 7 个，554 复测正要用 --smoke）；PLAN 早期章节回写（阶段 5"未写任何邮件代码"与事实冲突、§8 面板"密钥不经网页"旧安全模型、8000 端口残留、§4 目录树）；ND_CERTBOT_EMAIL 默认值为个人邮箱且随 Release 附件分发（仓库转公开前处理）；`.bak-*` 备份无限累积加"保留最近 5 份"裁剪。

## 五、最终意见

**拦下：当前状态不发 v1.0.0。**

理由：八个阻塞项里有两个"必然爆炸"（P0-1 证书 90 天后过期且当前代码路径已无法自愈、P0-5 回滚链整体为空使发版门槛的演练无法进行）、两个实证攻击面（P0-2 存储型 XSS、P0-3 供应链回环）、一个反功能缺陷（P0-4 每次部署抹掉面板改动——这会持续毁掉本周搭的核心功能）。它们的共同病根是**文档承诺与脚本行为脱节**，而非设计缺失；合计修复量约百余行代码 + 一次凭据轮换，一个工作日内可清完。

放行路径：修复 P0-1~P0-7 并全量测试 → 执行 P0-8 轮换 → deploy.bat 上一版 rc7 → 07-28/29 两个观察周期 → 回滚演练（此时 DEPLOYED.log 已有真实 digest 可演）→ send-email --smoke 复测 → merge main、按 P0-7 的预检推 v1.0.0。乐观估计 **07-29~07-30 可发正式版**。

底子值得肯定：结构性安全设计（容器加固、最小权限 CI、参数化 SQL、autoescape 纪律、SSRF 防护）与测试文化（106 项+事故回归）高于同规模项目均值；本次拦下的问题全部集中在"胶水层"——恰恰是单人项目最容易失守、也最值得在 1.0.0 门口守住的地方。
