## 1. 本次取舍

按用户要求，以小规模网站的实际收益为标准。主线是修复全部已识别的架构缺陷，同时保持实现简单：先处理数据一致性、自动单句重译、资金权益和恢复边界，再处理可观测性与配置治理。继续使用 Python、SQLite、Jinja2、Compose 和 systemd。

句子重译的目标是自动失败恢复：校验失败且可定位具体句子时，模型只重译失败句，自动合并并复校。此前规划加入的人工选句、候选审核和应用流程取消，不是本次需求。

- B/C/A/O 类架构缺陷全部进入必修范围：内容提取与发布、任务和事务、付款与权益、配置、备份恢复、健康检查、日志和 CI 均需收口。
- 保持小步实现：不引入微服务、配置中心、消息中间件或安全平台；访问边界只做现有站点所需的目录与授权修正。
- 资金对账、退款记录、配置 revision、备份恢复演练和业务状态检查都是架构闭环的一部分，可分批交付，但不能从计划中删除。
- U 类纯产品体验和经营扩展（SEO、学习闭环、增长分析等）不属于本轮架构必修项，继续按需求评估。
- 现有登录、Admin 认证、支付验签、金额核对、密码保护和投递幂等继续使用；不追加高强度安全平台或逐项人工审批，但保留架构闭环所需的最小业务记录。

架构缺陷不得以“当前规模小”永久跳过；只允许按风险分批实现。完整范围和产品类可选项见 SYSTEM_REVIEW 的第 0 节。

## 3. 最小架构

### 3.1 运行职责

Site 继续负责账号、会员阅读和验证码 outbox；Admin 负责配置与操作；现有 worker 负责日报生成和恢复。验证码不等待长翻译锁。保留现有 Compose 服务，暂不退役 Web、不替换 HTTP 框架、不新增后台对账服务。

日常生成与恢复共用一个 worker 锁，保留已有 task、attempt、action、lease、circuit 和 `task_capabilities`。只迁出当前修改确实需要的共用逻辑，不按文件行数拆模块。

内部 manifest 和正文快照不由通用静态入口返回；所有文件返回分支共用目录范围检查，继续使用现有阅读授权。无需建立完整公开资源登记平台，也无需重写路由；此局部修正与发布代码一起交付。

### 3.2 内容的事实来源

| 对象 | 权威来源与用途 |
|---|---|
| 抓取候选 | 现有 articles/briefs 池，用于首次选题 |
| 刊期成员 | 新增 `edition_items`，按 `(edition_date, article_id)` 唯一，固定顺序和原文/分句快照 |
| 当前执行 | 每个 item 引用一个 `active_task_id`；旧 provider task 仅作为历史 |
| 翻译结果 | item 保存完整 `TranslationResult`，包括 `sentences_zh`、source hash 和 result revision |
| 发布事实 | 私有 manifest 及持久发布记录，覆盖刊期、文章身份、generation 和 result revision |
| 邮件事实 | 现有收件人级 delivery 记录，正式邮件、测试和验证码各自保持语义 |

文章身份独立于标题；新页面路径保证唯一，旧链接保持兼容。保留提取结果中的正常短段落，不再按少于 30 字符一律删除；提取成功不证明原站全文完整，不建设额外完整性评分系统。

首次选题固定成员，`target_count` 从主文成员数派生，来源不足时可少于 6。resume/build 不重新选题；同一 URL 可以属于多个刊期，各自保存快照。

完整句级结果在 R1 入库，不能等到 R3 才补。有效缓存继续复用，但不能作为唯一句子映射存储。每次新 attempt 记录执行时的 provider 身份，重绑定切换 active task，不改写旧尝试。

当前根 manifest 仅记录最新刊期，HTML release 只保留 5 个。新增多刊期发布索引及必要持久元数据，仍有限保留 HTML；不建设全量文章版本平台。构建确认成员各有对应文件且路径不冲突。

### 3.3 必要事务

1. 提交前核对 active task、source hash、owner 和 attempt，防止旧执行覆盖新结果。
2. 完整译文、task/attempt 成功、result revision 和 dirty generation 在一个 SQLite 事务内提交；网络与渲染在事务外。
3. build 从固定快照生成，发布后按 manifest 确认上线；发布与数据库确认之间中断时可恢复，不重新翻译。
4. 完成数按目标文章覆盖率计算，重复 provider 成功不能补足另一篇失败。
5. 不要求数据库与文件系统跨介质原子事务，只保留必要的发布对账恢复。

## 4. 调度与翻译规则

- daily 抓取、选题并首次创建刊期；resume 只消费已保存待办，不抓取、不 reseed、不移动成员。
- ready 判断只看当前任务和现有 capabilities。无翻译待办但 build debounce 尚未到时，等待构建到点后完成；无任何待办正常退出。
- 一次文章执行默认共享 600s 总预算、最多 3 个 provider 请求；首次请求、自动单句重译与必要的整篇结构修正共同计数，不给修复另开一套时限。慢模型可沿用配置提高预算，lease 与 worker 上限同步匹配。
- 自动重试只由持久调度器管理，默认每篇每刊期最多 3 次自动执行；失败后保留人工操作。取消和超时传播到任务层，不被软修复吞掉。
- 保留 JSON 可解析、正文非空、段句位置与数量明确、source hash 一致和合理大小限制；位置契约不承诺证明全部语义正确。
- 数字、实体、否定和长度信号只提示，不阻断、不自动请求。取消标题 40 字及教学内容固定数量的整篇拒绝条件。
- 教学字段缺失或形状不合法时过滤、降级为空，正常正文保留；取消新建词汇出处匹配器和大规模语义评估体系。
- 保留有效整篇缓存；repair protocol 更新不统一作废旧缓存，缓存命中不自动发起数字修复。只记录请求数、耗时和必要错误，取消诊断平台及固定 7 天诊断文件制度。

这些是待实现的新规则，不代表 t26 已全部具备。测试以已发现缺陷的少量离线回归为主，不以“所有语义错误必须被检出”验收。

## 5. 校验失败后的自动单句重译

R3 首次交付就是自动修复，使用当前文章的同一 task 和 worker。流程为：整篇响应 → 校验并定位失败句 → 模型重译该句 → 自动合并 → 重新校验 → 提交与构建。正常路径不需要人工操作。

### 5.1 触发范围

| 校验结果 | 自动处理 |
|---|---|
| 段落数和句数匹配，但具体槽位为空或非字符串 | 可准确定位 `P#S#`，进入单句重译 |
| 有现行有效的句级失败规则，且错误能唯一关联原句 | 只修该失败句；不为此新增校验器或恢复已取消的规则 |
| JSON 无法解析、正文数组缺失、段数或句数不匹配 | 当前位置式协议无法可靠定位单句，不猜位置；沿用剩余预算内的整篇结构修正，仍失败则结束任务 |
| 数字、实体、否定、长度等软诊断 | 仅提示，不触发自动重译；此前取消数字硬门的决定不变 |
| 标题、摘要或教学字段错误 | 按对应字段规则处理，教学附属字段可降级；不误触发正文单句修复 |

### 5.2 最小实现闭环

1. JSON 解析后先检查段句形状并保留未通过校验的候选数据。对可定位错误返回具体 `P#S#` 和失败原因，而非只抛出“第几段含空句”并丢弃候选。局部修复不能要求输入先成为完全有效的 `TranslationResult`。
2. 同一执行中自动取出失败句，传入冻结原句、当前无效译文、失败原因及必要相邻上下文。每次模型请求只重译一个目标句；多个失败句按位置顺序处理，不重新请求已经合格的句子。
3. 单句响应只包含目标编号和 `translation_zh`。核对编号与内容后替换候选中的对应槽位，保留其余正文和正常教学字段，再重新校验。
4. 复校仍有可定位失败时，只在第 4 节的剩余请求和时间预算内继续处理失败句；取消或超时立即停止。预算耗尽仍有硬错误则任务失败并记录原因，不发布残缺结果，也不无限重试。
5. 完整结果通过现行校验后，才按 R1 事务提交译文、task 成功与构建意图；已有有效版本在此之前保持不变。检查当前 source hash 和任务所有权，防止旧执行覆盖新结果。
6. 沿用现有 attempt 记录修复位置、原因、请求数和结果。无需人工选句 UI、候选审批状态、单独修订动作表、句子 worker 或单句缓存；不扫描重翻历史，也不对有效缓存自动发起修复。

暂停草稿可复用单句 prompt/parser、合并器和原文快照逻辑；当前 `InvalidTranslation` 仍优先走整篇反馈重译，现有单句草稿又主要处理已通过校验结果上的数字诊断，触发位置需要调整。整篇 cache key 变更、缓存命中数字修复、独立单句缓存和数字 evidence 循环不按原路线接入。

## 6. 邮件、资金与运维闭环

正式邮件继续要求有效会员、主动订阅、当日窗口及已发布内容。零目标显示 `skipped/no_eligible_recipients`，与 `already_sent` 区分；超窗、未启用、明确失败和 `unknown` 保持可读原因。

已发送的不重发，`unknown` 不自动重发。沿用现有 SMTP 阶段记录和日志，Admin 展示目标/有效/上线篇数与邮件结果即可；取消新的健康分层、监控告警和人工邮件后台队列工程。

以下是必须完成的独立架构增量，不要求互相等待：

| 问题 | 最小交付 |
|---|---|
| 取消订单后的迟到到账 | 保留订单与结算依据，验签/金额/交易核对通过的迟到结果进入异常状态并可完成权益或退款处理；不能静默丢失资金事实。 |
| 人工赠送并发覆盖 | 将“增加 N 天”移入一次事务中读取和累加，统一付款、兑换、人工命令的权益合并与幂等。 |
| 配置部分写入 | 明确权威配置、revision、生效状态和失败恢复；保存结果不得误报全部回滚或生效，投影可重建。 |
| 备份与恢复 | 保留 online backup；补日常备份覆盖和恢复演练，离线覆盖恢复需停止 Site/Admin/worker 等全部写入者，并核对备份后新增付款/投递。 |
| 后台对账与退款状态 | 增加有界待核对订单、异常到账和退款/争议引用的持久状态，避免依赖用户打开账户页；不要求接入复杂财务平台。 |
| 业务健康与告警 | 在现有日志和页面增加刊期、任务、邮件、outbox、备份年龄等业务状态检查；异常通知只在持续失败或恢复时触发。 |
| 配置解析与 CI | 统一重复键和入口优先级；将离线验证复用到 PR/main，tag 发布继续执行相同验证。 |

便宜且与当前修改相邻的架构修正可顺手处理：未来异常日期过滤、正文失败原因保留、简讯来源筛选、到期账号仍可关闭简报、重复配置键处理和 `.env` 忽略规则。免费/付费矛盾文案属于 U 类产品修正。
