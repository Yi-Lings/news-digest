## 1. 1.2.19 本次修复

`v1.2.19` 是翻译分句兼容性维护版，业务范围没有扩张：

- 完善英文首字母缩写的句子边界处理，覆盖两字母首字母缩写。
- 避免 `a.m.` / `p.m.` 等时间表达被错误合并或拆分。
- 降低正常模型输出被错误判为 `SCHEMA_VALIDATION_FAILED` 的概率。
- 不新增账号、会员、订单或支付能力；数据库 schema 仍为 `7`。

## 2. v1.2.19 实际包含的全部能力

### 2.1 每日双语新闻流水线

- 每天 `08:00 Asia/Shanghai` 由 systemd timer 启动。
- 抓取并聚合 BBC News、The Guardian、NPR、DW、Al Jazeera、France 24 等已配置来源。
- 在最近时间窗口内去重、评分和选题，默认生成 6 篇主文章，其余合适内容进入简讯。
- 保存来源、作者、发布时间和原文链接；正文抓取失败时可退回来源摘要。
- 生成报纸风静态站点，保留按日期归档、稳定刊期 URL 和 `current` 原子切换。
- 页面支持英文、双语、中文阅读模式，偏好保存在浏览器端；文章提供朗读和学习内容。
- 文章页提供双语摘要、词汇、搭配、长难句解析；原文链接始终指向出版方。

### 2.2 翻译协议与逐篇任务

- 支持 OpenAI Chat Completions 与 Anthropic Messages 两种配置驱动协议，支持流式和非流式响应。
- provider 通过 `providers.json` 管理，支持启停、唯一默认 provider、固定 `Hi` 连接测试和配置指纹。
- 每篇文章都有持久化翻译任务，任务状态包括：
  `pending`、`running`、`failed`、`retry_wait`、`succeeded`、
  `configuration_blocked`、`cancelled`。
- 同一篇文章同一时刻只有一个 lease；服务重启后可恢复任务、租约和动作审计。
- 正式输出要求 JSON schema：标题、摘要、逐段逐句中文译文、词汇、搭配和长难句解析均需满足数量与非空校验。
- tag 中的翻译 prompt 版本为 `p7`；`sentences_zh` 按段、按句与原文对应，缓存按 prompt/provider 身份隔离。
- 已成功的文章可以进入增量 build；失败文章不会抹掉同刊期已经成功的译文。

### 2.3 翻译失败、重试与熔断

- 只在请求明确结束并落库后计算下一次重试时间；运行中的请求不预创建重试。
- 可恢复基础设施错误按 `15 秒 → 30 秒 → 60 秒 → 2 分钟 → 5 分钟`退避。
- 同一 provider 连续 5 次基础设施失败后进入熔断；熔断只暂停该 provider 的新翻译，不停止站点、Admin 或已上线内容。
- 熔断探测冷却依次为 `60 秒 → 2 分钟 → 5 分钟`，同一时间只允许一个探测 lease。
- HTTP `400/401/403`、余额/权限拒绝统一为 `UPSTREAM_ERROR`，可按 provider 错误恢复；只有本地配置前置校验错误使用 `CONFIGURATION_INVALID`。
- `RATE_LIMIT_429`、`PROVIDER_5XX`、`NETWORK_CONNECT_FAILED`、`REQUEST_TIMEOUT` 可进入基础设施重试。
- `EMPTY_RESPONSE`、`UNPARSEABLE_RESPONSE`、`SCHEMA_VALIDATION_FAILED`、`TASK_DATA_MISSING` 保留为可见的单篇失败，等待人工重试，不应让整期任务消失。
- Admin 可执行“立即调度”“立即重试”“立即探测”和“终止”；重复点击依靠持久动作与 lease 幂等化。
- 终止请求先等待旧执行体确认结束，再把任务转为可重试状态；不会直接强制创建第二个 provider 请求。

### 2.4 增量 build、刊期和邮件

- 单篇翻译成功后进入当日刊期的增量 build；build 使用临时目录、校验和原子 `current` 切换。
- 所有目标文章翻译成功、最终 build 成功后，刊期才进入 `complete`。
- 邮件只在刊期完成后投递；成功收件人不会因重跑、重启或翻译重试而重复发送。
- 投递按收件人记录 `pending`、`sending`、`sent`、`failed`、`unknown` 等状态。
- SMTP 支持 implicit TLS 和 STARTTLS；连接测试不发信，测试邮件和正式投递需要显式确认。
- SMTP DATA 阶段连接中断时记录 `unknown`，默认不盲目重发，以避免服务端已经接收邮件造成重复。
- 已过投递窗口的旧刊期标记为 `DELIVERY_EXPIRED`，保留内容和投递审计，不自动补发历史刊期。

### 2.5 公开订阅与退订

- 首页提供公开订阅表单；提交后通过 double opt-in 确认，未确认地址不会进入正式投递。
- 公开订阅和 Admin 手工添加使用同一份订阅名单；正式投递只选择 `active` 记录。
- 支持确认链接、退订链接、`List-Unsubscribe` 和 RFC 8058 one-click unsubscribe。
- Admin 可新增、停用、启用、删除订阅记录，并只显示脱敏邮箱和短标识。
- 订阅名单代表邮件收件资格，不代表用户账号、会员资格或付费权益。
- 订阅、确认和退订 API 由 Admin/preview 服务提供，静态站点通过 Nginx 转发；没有用户中心。

### 2.6 Admin 运维面板

v1.2.19 的 Admin 是面向流水线运维的面板，主要包含以下工作区：

| 工作区 | 能力 |
|---|---|
| 模型接口 | provider 配置、启停、唯一默认、连接测试、受控探测 |
| 邮件设置 | SMTP 配置、邮件版式/数量/来源设置、预览、连接测试、单账号测试邮件 |
| 订阅管理 | 统一名单的脱敏查看、新增、停用、启用、删除 |
| 翻译状态 | 逐篇任务、阶段、重试时间、错误代码、熔断、调度/重试/终止/探测 |
| 投递状态 | 刊期和收件人投递结果、失败与 `unknown` 的受控重试 |

面板使用登录页、会话 Cookie 和 CSRF 保护。API key、SMTP 密码、面板口令和原始 provider 响应不在页面或审计记录中回显。

### 2.7 部署、数据和安全基线

- 生产通过 GitHub Actions 构建 GHCR worker/web 镜像，部署使用同一 Release 的 immutable digest。
- Docker Compose 提供一次性 worker、静态 web 和常驻 Admin；服务器不检出源码、不在部署阶段构建镜像。
- systemd timer 负责每日任务，wakeup path 负责唤醒恢复 worker；每日 worker 与恢复 worker 共用宿主锁。
- Nginx 负责 HTTPS、回环端口反代、安全响应头和公开订阅 API 路由。
- SQLite 保存文章、译文、翻译任务、订阅、投递状态和审计；schema 迁移前执行 online backup。
- 站点构建失败时继续保留上一份有效 `current`；部署脚本做目标校验、镜像 digest 绑定、备份和健康检查。
- 抓取 URL、重定向和响应大小受限；外部链接经过协议校验；敏感配置只落服务器受限目录。

## 4. 与 v1.4.0 的明确差异

`v1.2.19` 是“新闻流水线 + 邮件订阅”的版本；`v1.4.0` 候选版在此基础上增加了完整账号和付费产品。下表只列实现层面的关键差异：

| 领域 | `v1.2.19` | `v1.4.0` 候选 |
|---|---|---|
| 产品对象 | 读者通过公开订阅接收邮件 | 读者拥有账号，并可购买月刊/年刊会员 |
| 登录/注册 | 无用户账号、无登录、无忘记密码 | 邮箱验证码注册；邮箱+密码登录；邮箱验证码只用于重置/改密 |
| 会员权益 | 不存在付费会员，订阅仅是邮件收件资格 | 会员资格控制正文阅读和每日简报资格，并显示到期时间 |
| 支付 | 无订单、EasyPay、卡密或收款核验 | EasyPay 兼容支付、订单、金额冻结、回调验签、卡密兑换 |
| 价格 | 无基准价、现价和折扣设置 | Admin 以元设置月刊/年刊划线价、现价和绿色折扣标识 |
| 管理账号 | 只有流水线 Admin 面板账号 | 站点账号可授予/撤销管理员角色；用户管理独立成页 |
| Admin 结构 | 模型接口、邮件、订阅、翻译、投递 | 用户管理与付费管理分开，另保留翻译/投递等运维区 |
| 公共站点 | 静态 web；订阅 API 经 Admin/preview 转发 | 独立 Site 服务处理注册、登录、账户、订单和付费墙 |
| 运行端口 | web 与 Admin 为主要服务 | web `8618`、Admin `8619`、Site `8620` 分离 |
| 数据库 | schema `7` | schema `10`，包含账号、会员、订单和资格/投递终态扩展 |
| 翻译质量 | 严格逐句 schema 与 p7 分句器 | 增加质量硬门、分句版本冻结、内容级校验和更完整的恢复治理 |
| 投递资格 | `active` 订阅即可成为收件人 | 每次 SMTP DATA 前重新检查有效付费会员资格 |
| 站点页面 | 首页、文章、归档、隐私和订阅区 | 增加注册、登录、忘记密码、账户、会员订阅、订单、联系我们等页面 |
| 部署隔离 | Admin 可触及 `/config` 与共享数据边界 | Site 只读独立 `site-config`，不挂载 provider 配置；部署前后门禁更严格 |

### 4.1 不要混用的概念

- v1.2.19 的“订阅”是邮件名单记录，不等于 v1.4.0 的“会员订阅”。
- v1.2.19 的 Admin 账号不能直接当作 v1.4.0 的站点用户账号。
- v1.2.19 的静态首页不会出现 v1.4.0 的账户、订单和支付页面。
- v1.2.19 的 schema `7` 不能用 1.4.0 的字段查询；升级必须走正式迁移，不要手工删库或重建卷。
- v1.2.19 的旧配置项和端口不能作为 1.4.0 的完整配置说明；部署应使用目标 Release 的部署包和 `digests.env`。

## 5. 从 v1.2.19 升级到 v1.4.0

1. 保留 `news-data`、`news-site`、`config` 和既有备份；不要执行 `docker compose down -v`，不要删除 SQLite。
2. 使用同一 1.4.0 Release 的部署包与 worker/web immutable digest；不要混用 tN 候选、旧镜像 tag 或手工查询到的 digest。
3. 部署前冻结 timer、wakeup path、daily worker 和 resume worker，先做 SQLite online backup 与 SHA-256 校验。
4. 让官方迁移逻辑把 schema `7` 升到 `10`；若迁移失败，停止部署并使用备份回滚，不要强行启动新 worker。
5. 升级后先验证 Web/Site/Admin 回环健康、schema、`integrity_check`、镜像 revision、Nginx HTTPS 和 systemd 调度，再配置账号/支付/SMTP。
6. 原有 v1.2.19 邮件订阅记录需要按 v1.4.0 的会员资格规则重新核对；不要因为旧订阅记录存在就自动赋予付费会员权益。
7. 公开支付、真实 SMTP、provider 和历史补发都必须单独授权；部署本身不应触发这些业务动作。

## 6. v1.2.19 的旧版操作入口

本地演示和运维命令以该 tag 的 CLI 为准：

```text
news-digest fetch
news-digest build
news-digest translate [--date YYYY-MM-DD] [--yes]
news-digest run --yes
news-digest resume-automation --yes
news-digest import-edition FILE
news-digest preview --port 8618
news-digest preview-email [--date YYYY-MM-DD]
news-digest send-email --date YYYY-MM-DD --yes
news-digest admin --port 8619 --config-dir /path/to/config
```

其中 `send-email --yes` 会触发真实 SMTP；没有明确授权时只使用预览或 fake 测试。线上升级、备份、回滚和错误处理以对应 Release 的 `deploy/README.md` 与 `docs/OPERATIONS.md` 为准。
